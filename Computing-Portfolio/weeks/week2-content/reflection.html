Critical Reflection

The main point I have taken from this week's study is that software performance is affected by design choices made before the program is executed. It is possible to write code that produces the correct answer but becomes impractical when the amount of data increases. Big-O notation provides a way of identifying this risk by showing how processing or memory requirements grow (Cormen et al., 2022). I also understand more clearly that this is a model of growth rather than a prediction of exact execution time.

The comparison between linear and binary search made this particularly clear. Linear search is simple and works with unsorted information, but its processing grows directly with the dataset. Binary search is considerably more efficient for large collections, although it requires sorted data and suitable indexed access. This shows that an algorithm cannot be evaluated separately from its data structure. Binary search would lose much of its advantage on a linked list because reaching the middle item requires traversal.

I also recognised that theoretical efficiency is not the only concern. Linked lists can provide efficient insertion, but arrays may perform better in practice because their values are stored together in memory. Merge sort gives predictable performance but uses additional storage. Quick sort may be faster in practice, although poor pivot selection can create quadratic behaviour. These examples show that performance involves trade-offs between speed, memory, predictability and implementation complexity.

Database selection creates similar consequences. A relational database provides strong constraints and transactional consistency, while a NoSQL database may provide greater structural flexibility and easier horizontal distribution. However, I now recognise that these are not absolute categories. PostgreSQL supports sophisticated concurrency control, while document databases can support transactions and references (PostgreSQL Global Development Group, 2026; MongoDB, Inc., 2026). Choosing either approach without considering the actual data relationships could create unnecessary complexity or unreliable information.

In professional development, I would now consider the expected data volume, common operations and growth of the system before selecting an algorithm or structure. I would also combine complexity analysis with profiling because Big-O does not include every practical cost. The area I need to develop further is implementing and benchmarking these algorithms in Python using realistic datasets.

Reflection Summary

Most significant concept: an algorithm must be evaluated together with its data structure.

Professional relevance: poor choices can affect response time, memory use, scalability and maintenance.

Further development: practical benchmarking and profiling with Python.
