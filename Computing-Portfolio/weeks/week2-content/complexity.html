Big-O Notation

Big-O notation describes an asymptotic upper bound on how an algorithm's resource requirements grow as the input size increases. It focuses on the dominant growth term and ignores fixed constants and smaller terms (Cormen et al., 2022).

For example, an operation count of 3n + 10 is described as O(n), because the linear term dominates as the input becomes large.

Common Complexity Classes

Complexity Name Typical Example Effect of Growth
O(1) Constant Accessing an array item by index Work remains approximately unchanged.
O(log n) Logarithmic Binary search Input can grow significantly with little extra work.
O(n) Linear Linear search Work grows in proportion to input size.
O(n log n) Linearithmic Merge sort Efficient for general comparison sorting.
O(n²) Quadratic Nested comparison loops Becomes expensive as the dataset grows.

Time and Space Complexity

Time complexity represents the growth in processing operations. Space complexity represents growth in memory use, including temporary structures and recursive call stacks.

A faster algorithm may require more memory. Merge sort, for example, provides predictable O(n log n) time but commonly requires O(n) additional space. An in-place quick sort implementation may use less additional memory, but its worst-case execution time is O(n²). The decision is therefore a time-space trade-off rather than a simple choice between a fast and a slow algorithm (Cormen et al., 2022).

Merge Sort and Quick Sort

Merge Sort

Merge sort has predictable performance and is stable, meaning equal values retain their original order. This is useful where records contain several fields and the existing order has meaning.

Its main disadvantage is the additional storage normally required when merging sections.

Quick Sort

Quick sort frequently performs well because its memory access pattern can be efficient. Performance depends on selecting a suitable pivot.

If the pivot repeatedly creates highly unequal partitions, the algorithm approaches O(n²). Randomised or median-based pivot selection can reduce this risk.

Limitations of Big-O

Big-O does not provide an exact execution time. Two O(n) algorithms may have very different constants and implementation costs.

Small datasets may not show a meaningful difference between algorithms. Hardware caching, disk access, network delays and programming-language overhead can also dominate theoretical complexity.

Complexity analysis should therefore be combined with profiling and testing using realistic data. This is particularly important where cache behaviour, storage latency or language runtime overhead is likely to dominate the abstract operation count.
