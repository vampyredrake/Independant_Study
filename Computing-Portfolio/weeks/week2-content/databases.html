SQL and NoSQL Databases

Structure, Consistency, Scalability and Use Cases

Overview

SQL and NoSQL databases address different data management requirements. Relational databases emphasise structured relationships, constraints and transaction consistency. NoSQL systems often emphasise flexible models, distribution and large-scale workloads. The categories overlap, however, because modern relational systems support semi-structured data and some NoSQL systems provide multi-document transactions.

Comparison Table

Data model Tables, rows, columns and relationships. Documents, key-value pairs, graphs or column families.
Schema Usually predefined and strongly controlled. Often flexible or application controlled.
Query approach Standardised SQL. Varies between database products.
Consistency Commonly supports strong ACID transactions. May trade immediate consistency for availability or distribution.
Relationships Strong support through keys, joins and constraints. Often stores related information together to reduce joins.
Scaling Traditionally vertical, although distributed relational systems also exist. Often designed for horizontal scaling across several servers.
Typical use Finance, bookings, inventory and structured business systems. Content systems, event data, distributed services and rapidly changing datasets.

Relational Example 

STUDENTS
--------------------------------
student_id | name       | course
1          | David      | BSc Computing

ASSIGNMENTS
--------------------------------
assignment_id | student_id | mark
101           | 1          | 68

The foreign key in the assignments table links each assignment to a student. Constraints can prevent an assignment from referring to a student who does not exist. 

SELECT students.name, assignments.mark
FROM students
JOIN assignments
    ON students.student_id = assignments.student_id;

Document Database Example 

{
    "studentId": 1,
    "name": "David",
    "course": "BSc Computing",
    "assignments": [
        {
            "assignmentId": 101,
            "mark": 68
        }
    ]
}

The related assignment data is embedded inside the student document. This can make retrieval simple, but duplicated embedded data can become difficult to keep consistent if the same information appears in several documents.

ACID Transactions

  • Atomicity: a transaction completes fully or not at all.
  • Consistency: a transaction preserves defined rules and constraints.
  • Isolation: simultaneous transactions do not create invalid interference.
  • Durability: committed information remains stored after a failure.

These properties are particularly important in systems such as payments and stock control, where partial updates could create incorrect results. PostgreSQL defines ACID as atomicity, consistency, isolation and durability, with the purpose of preserving validity during concurrent operation and failures (PostgreSQL Global Development Group, 2026).

Critical Evaluation

SQL is suitable when relationships, validation and transactional accuracy are central requirements. Its schema provides control, although significant structural changes may require migrations. Transaction isolation also introduces trade-offs: stronger isolation can reduce anomalies but may increase waiting, retries or contention under concurrent workloads (PostgreSQL Global Development Group, 2026).

NoSQL can be suitable when data structures vary, workloads are distributed or access patterns favour embedded documents. However, flexibility does not remove the need for design. MongoDB's documentation distinguishes embedding from referencing and links the choice to access patterns and data relationships (MongoDB, Inc., 2026). Poorly controlled documents can still create inconsistent data and duplicated business rules.

The two approaches are not mutually exclusive. A system may use a relational database for transactions and a document or analytical database for logging, caching or high-volume event data.
